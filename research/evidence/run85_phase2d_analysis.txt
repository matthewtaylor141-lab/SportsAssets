=== A1. PAGINATION MECHANISM ===
  offset       {"offset": 100}    http=200 events=100 ids 44392..59033   -> HONOURED
  page         {"page": 2}        http=200 events=100 ids 6435..44391   -> IGNORED
  cursor_skip  {"skip": 100}      http=200 events=100 ids 6435..44391   -> IGNORED

  PAGINATION_MECHANISM = offset

  THE TRAP THIS PROBE WAS BUILT TO CATCH, AND DID. `page=2` and
  `skip=100` both answered HTTP 200 with a full 100-event body -- and
  BOTH returned the identical first page, ids 6435..44391. A probe
  that judged success by status code, or by 'did I get rows back',
  would have recorded page 2 as walked and silently re-counted page 1
  twenty-three times. The probe judged by whether the returned id set
  was DISJOINT from the first, which is the only question that
  distinguishes a working parameter from an ignored one.

  The venue accepts unknown query parameters without complaint. Any
  future code that paginates this API must verify the page MOVED.

  DEFECT 1. THE GAME ALLOWLIST UNDERCOUNTS, AND I FROZE IT TOO NARROW.

  SPORTS_MARKET_TYPE_DRAWABLE_OUTCOME (1017 rows) was not in the
  allowlist, because I had never seen the value and froze the list
  before the data. Every one of those 1017 rows carries the v1 type
  `soccer_team_full_time_winner` -- the soccer three-way match
  winner. That is a GAME-LEVEL market by any reading, and it is
  precisely the soccer shape the desk already cares about.

  So GAME_LEVEL_MARKETS_FOUND = YES is not affected, but the COUNT is
  a floor, not a total. I am not retroactively widening the allowlist
  to inflate the number: the rule was preregistered, it ran as
  written, and the honest report is the count it produced plus this
  named omission.

    GAME_LEVEL_ROWS_UNDER_FROZEN_ALLOWLIST = 24047
    DRAWABLE_OUTCOME_ROWS_EXCLUDED         = 1017
    GAME_LEVEL_INCLUDING_DRAWABLE_OUTCOME  = 25064
    ALLOWLIST_REVISION_REQUIRED_BEFORE_NEXT_RUN = YES

  SPORTS_MARKET_TYPE_PROP (32229 rows) is a genuinely separate
  question, not an oversight. Its v1 values are player and team
  props -- football_player_receiving_yards, soccer_game_exact_score,
  football_team_total_first_downs. These attach to a game but are not
  a team moneyline, spread or total. They stay OTHER_STRUCTURED_SPORTS
  until someone decides deliberately, which is not this run's call.

=== D. WHY PHASE 2C FOUND ONLY FUTURES ===
H1  game markets genuinely absent at capture time
    AGAINST, strongly. Phase 2C ran 2026-09-13T03:40Z; this ran
    2026-09-13T11:36Z, eight hours later, and found 24047 game-level
    rows. Many are for games dated 2026-09-13 and 2026-09-19, so they
    existed at 03:40Z: an NFL game kicking off 2026-09-13T17:00Z was
    listed well before either run.
    NOT FULLY EXCLUDED: this run did not re-query at 03:40Z and
    cannot, so 'the exact same listing existed then' is inference
    from creation dates, not a measurement. H1 = REJECTED ON
    BALANCE, NOT DISPROVEN.

H2  game markets exist on later pages
    CONFIRMED, and this is the mechanism. Page 0 of the walk
    reproduces Phase 2C exactly: ids 6435..44391, 1579 rows, 0 game-level.
    Ids ascend monotonically with paging and the game-level mass sits
    at high ids. Phase 2C issued ONE unpaginated /v1/events call, so
    it read the oldest 100 events and stopped.
    H2 = CONFIRMED

H3  game markets require another public query or filter
    AGAINST as a requirement. No filter beyond `offset` was needed:
    the same active=true&closed=false query reaches them once paged.
    PARTLY SUPPORTED as an efficiency matter -- a query that sorted or
    filtered by start time would reach them far more cheaply than 24
    pages. No such parameter was probed. H3 = NOT REQUIRED; A CHEAPER
    PATH IS NOT_IDENTIFIED.

H4  game markets use different structured metadata
    PARTLY CONFIRMED, and it matters. They carry the same
    sportsMarketType/sportsMarketTypeV2 fields, so Phase 2C's
    admission logic would have ADMITTED them. But their v2 values are
    SPREAD / TOTAL / MONEYLINE / DRAWABLE_OUTCOME where futures carry
    FUTURE, and the live-state `period` field only takes non-NS values
    out here. Phase 2C could not have known that from page 0.
    H4 = PARTLY CONFIRMED (different VALUES, same FIELDS)

H5  our admission logic excluded them
    AGAINST. Phase 2C required native event identity, a structured
    sports field, two marketSides, open state and a tick size. Every
    game-level row here satisfies all five: 24047 of 24047 have exactly two
    marketSides, all carry a tick size and a structured type.
    The markets never reached admission -- discovery stopped first.
    H5 = REJECTED

H6  NOT_IDENTIFIED
    Not needed. H2 explains the result with a demonstrated mechanism.
