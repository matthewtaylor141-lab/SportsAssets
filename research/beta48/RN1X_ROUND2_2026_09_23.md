## 1 · The prospective lane

### The lane could not have worked, and I had called it ARMED

`cycle()` returned `IDLE_NO_CANDIDATES` **before** `_save_cursor`. The
seed existed only inside that return value, so the next cycle found no
stored row, re-seeded at the **new** head, and every row that had arrived
in between was skipped permanently. The only candidate it could ever
catch was one inserted between `max(id)` and the query microseconds
later — a race, not a design.

Production had said so plainly and I read past it four times:
`rn1x_prospective_cursor` was **absent** from `ingestion_state` while the
lane reported `IDLE_NO_CANDIDATES` every cycle, against **9,444 eligible
live BUYs a day**. I reported that lane as ARMED. It was blind.

The existing test could not catch it because it asserted what `_cursor`
**returns** and never that anything was **written**:

```python
got = await W._cursor(conn, PROSPECTIVE_CURSOR_KEY, seed_at_head=True)
assert got == head          # true, and useless
```

## 3 · The independent model path

### The inventory corrected me

"Nothing is fitted anywhere" was **wrong**. `learn/kernel.py` is 892 lines
of standard-library estimators — Ridge by IRLS, Isotonic by PAV, boosted
depth-1 Stumps, a discrete-time Hazard, a BaseRate control — with
`learn/dataset.py` and `learn/ferrari.py` supplying two fitted targets and
`learn/metrics.py` refusing to report a score without its base rate.

| Question | Answer | Evidence |
|---|---|---|
| **Does an appropriate scorer exist for entry?** | **NO** | `T_COMPLETE` forecasts a complementary BUY within H; `T_CLEARS` adds that the pair clears parity. Both fitted, neither is settlement. `qualifies_for_entry` returns `R_MODEL_TARGET_MISMATCH` for both |
| **Do its live inputs reach the production decision function?** | **YES** — the part I expected to fail | All 14 shared features (and Ferrari's 3) are functions of the cohort fill row and that market's earlier fills, both of which the prospective lane holds at decision time. `feature_availability()` **computes** the vector from a production-shaped row; a test asserts `missing == []` |
| **Does its evidence qualify it?** | Unanswerable for entry while the first is NO | And the **order** matters: `qualifies_for_entry` refuses on TARGET before consulting any metric. Reading the numbers first is how a well-calibrated forecast of the wrong quantity gets promoted — the scores are excellent, for a question nobody asked |

The prospective ledger (migration 102) records target, model version,
dataset sha, feature sha and per-row feature availability **before** the
outcome exists; the label arrives later by UPDATE. Availability is a
property of the row scored, not of the model, so recording it afterwards
would be recording a guess.

**The schema had a hole and the test found it.** My CHECK constraints
happily accepted a row inserted with `outcome_known = true` and a label
attached — a description of the past wearing a prediction's clothes, which
is the one thing this table exists to prevent. A CHECK cannot tell an
INSERT from an UPDATE. I watched the assertion not raise, then added a
`BEFORE INSERT` trigger rather than softening the test.

Mutation-checked properly on the second attempt: dropping the trigger from
the **database** proves nothing, because the test re-runs the migration.
Removing the block from the **migration file** is what makes it fail.

**Nothing here feeds the entry gate.** A test hands `qualify_model` a model
with a fitted target, `FROZEN` status and `VALID_AS_ENTRY_TIME`
predictions — every requirement satisfied but one — and asserts
`refusals == [R_MODEL_TARGET_MISMATCH]` exactly, so it cannot pass for an
incidental reason.
