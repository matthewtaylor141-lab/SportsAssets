<p style="font-size: 16px;">Sharp Pinnacle prices — in-play and pre-game — paired with a live steam-move detector, served over a clean REST API (drop-in compatible with the formats you already use) plus optional push streams over Server-Sent Events. <h2 id="intro">Introduction</h2>
<p>Everything hangs off one host: <code id="baseUrl">https://pinnapi.com</code>. Read every path below as relative to it, and expect JSON back on every call.</p>
<p>Auth is a single <b>API key</b> — no username, no password; the key <em>is</em> your identity. Mint one free in a click from the <a href="/">landing page</a>.</p>

<div class="callout">
  <b>Already wired to another Pinnacle feed?</b> The <code>/kit/v1/*</code> responses follow the same shape as the common third-party formats — point your existing client at this base URL with your key and it should run as-is.
</div>

<div class="callout" style="background: rgba(52,211,153,.06); border-left-color: var(--accent);">

<!-- ─────────────────── Auth ─────────────────── -->
<h2 id="auth">Authentication</h2>
<p>Send your key any of three ways — we check them in this order:</p>
<ol style="color: var(--muted); line-height: 1.8; font-size: 14px;">
  <li><code>x-portal-apikey</code> header (recommended — matches legacy third-party APIs)</li>
  <li><code>x-api-key</code> header</li>
  <li><code>?key=</code> query parameter (useful for browsers / one-offs)</li>

<h2>Live odds</h2>
<p>A complete snapshot of everything live right now. The store is fed by Pinnacle's MQTT WebSocket, so each request hands back current prices — typically within the same 15–40 ms band as the push feeds.</p>

<!-- /kit/v1/markets -->
<div class="endpoint" id="markets">
  <div class="endpoint-head">
    <span class="verb get">GET</span>
    <span class="path">/kit/v1/markets</span>

  <div class="endpoint-body">
    <p>Hands back every event for a sport, each carrying its full market set — moneyline, spreads, totals, team totals — across all periods (full match, 1st half, 2nd half, and so on). Defaults to live; add <code>event_type=prematch</code> to read the pre-game feed instead.</p>

    <table class="param-table">
      <thead><tr><th>Name</th><th>Type</th><th>Description</th></tr></thead>

Category labels vary by sport — baseball &amp; basketball tag <code>"Player Props"</code>, soccer uses <code>"Team Props"</code>, some sports leave it blank — so match on the fields you actually need rather than assuming a fixed set. The same param works on <code>/kit/v1/prematch/markets?event_id=X</code> to return just one match's specials. Child events that are part of the match itself — such as tennis <code>(Games)</code>, see <a href="#tennis">Tennis</a> — are returned by default and need no flag. Specials do not fire drop alerts.

<h2>Prematch odds</h2>
<p>Pre-game lines for fixtures that haven't kicked off yet. A dedicated REST poller keeps them fresh (every few seconds), held in its own store apart from the live feed — so hitting prematch never steals cycles from the in-play snapshot.</p>

<div class="callout">
  <b>Which one do I call?</b> Reach for <code>/kit/v1/markets</code> when you want in-play prices and <code>/kit/v1/prematch/fixtures</code> for upcoming-fixture lines. Both speak the same sport IDs and the same event object, so a single field is all your code needs to branch on.
</div>

<h2>Dropping odds</h2>
<p>Catch price moves ("drops") as they happen on both the live and prematch feeds. A drop is emitted when an outcome's decimal odds fall by at least your threshold inside the configured window, and every drop ships with its <code>from</code> and <code>to</code> price alongside the full event context.</p>

    <h4>Subscribe protocol</h4>
    <p>Your client has 5 seconds after connecting to send a <code>subscribe</code> message. Subscribe by <b>sport</b> (the full firehose), by specific <b>event_ids</b> (a tight filter), or mix both in one message:</p>
<pre>{ <span class="k">"type"</span>: <span class="s">"subscribe"</span>,
  <span class="k">"streams"</span>:   [<span class="s">"live"</span>, <span class="s">"prematch"</span>],
  <span class="k">"sport_ids"</span>: [<span class="n">1</span>, <span class="n">2</span>],            <span class="c">// 1=Soccer, 2=Tennis — full firehose for the sport</span>
  <span class="k">"event_ids"</span>: [<span class="n">1631005165</span>]      <span class="c">// Pinnacle matchup IDs — narrow filter, just these events</span>
}</pre>
    <p style="font-size: 13px; color: var(--muted)"><b>Filter rule:</b> a frame is delivered if its sport_id matches a sport-level sub <i>or</i> its event_id matches an event-level sub. So <code>sport_ids:[2], event_ids:[12345]</code> means "all of Tennis plus this one specific event in any sport". Either field can be omitted but at least one is required.</p>
    <p style="font-size: 13px; color: var(--muted)"><b>Discovery pattern:</b> customers don't usually know matchup IDs upfront. Subscribe to a sport first → grep the snapshot for the events you care about (by team name, league, start time) → unsubscribe from the sport, subscribe to those specific event_ids. This narrows bandwidth to exactly the matches you're trading.</p>
    <p style="font-size: 13px; color: var(--muted)"><b>Per-stream cap:</b> 200 event_ids per connection per stream. Subscribing past the cap returns <code>{type:"error", code:"event_id_cap", ...}</code> and the request is rejected wholesale. A subscription lasts until you <code>unsubscribe</code> or the socket closes — an <code>op:"del"</code> does <b>not</b> end it (see <a href="#ws-del">what del means</a>), so send <code>unsubscribe</code> for events you are finished with if you cycle through many on one long-lived connection.</p>

    <h4>Server-sent messages</h4>
    <p>Immediately after each subscribe, one <code>snapshot</code> per subscription group:</p>
<pre><span class="c">// Sport-level subscribe → one snapshot per (stream, sport_id) with every</span>
<span class="c">// event currently in our store for that sport.</span>
{ <span class="k">"type"</span>: <span class="s">"snapshot"</span>, <span class="k">"stream"</span>: <span class="s">"live"</span>, <span class="k">"sport_id"</span>: <span class="n">1</span>,
  <span class="k">"events"</span>: [ <span class="c">/* full Pinnacle records, untouched */</span> ],
  <span class="k">"ts"</span>: <span class="n">1779200000000</span> }

<span class="c">// Event-level subscribe → one snapshot per batch of event_ids, with just</span>
<span class="c">// the records we currently have. Missing IDs appear in the stream once</span>
<span class="c">// Pinnacle pushes them.</span>

  <span class="k">"event_ids"</span>: [<span class="n">1631005165</span>],
  <span class="k">"events"</span>: [ <span class="c">/* full Pinnacle records, untouched (one per matched id) */</span> ],
  <span class="k">"ts"</span>: <span class="n">1779200000000</span> }</pre>

    <p>Then continuous frames as Pinnacle pushes / we poll:</p>
<pre><span class="c">// Live MQTT — `topic`, `op`, `rec` exactly as we received from Pinnacle.</span>

  <span class="k">"op"</span>: <span class="s">"upd"</span>,
  <span class="k">"rec"</span>: { <span class="c">/* Pinnacle record verbatim */</span> },
  <span class="k">"ts"</span>: <span class="n">1779200000123</span> }

<span class="c">// Prematch REST poll responses — `data` is the response array verbatim.</span>
{ <span class="k">"type"</span>: <span class="s">"prematch_matchups"</span>, <span class="k">"sport_id"</span>: <span class="n">1</span>,
  <span class="k">"arcadia_sid"</span>: <span class="n">29</span>,
  <span class="k">"data"</span>: [ <span class="c">/* /sports/29/matchups response verbatim */</span> ],
  <span class="k">"ts"</span>: <span class="n">1779200005000</span> }

{ <span class="k">"type"</span>: <span class="s">"prematch_markets"</span>, <span class="k">"sport_id"</span>: <span class="n">1</span>,
  <span class="k">"arcadia_sid"</span>: <span class="n">29</span>,
  <span class="k">"matchup_id"</span>: <span class="n">1631005165</span>,
  <span class="k">"data"</span>: [ <span class="c">/* /matchups/.../markets/related/straight verbatim */</span> ],
  <span class="k">"ts"</span>: <span class="n">1779200005230</span> }

    <p style="font-size: 13px; color: var(--muted); margin: 8px 0 0"><b>Fidelity contract.</b> <code>events</code>, <code>rec</code>, and <code>data</code> are never transformed. We only add envelope fields (<code>type</code>, <code>stream</code>, <code>sport_id</code>, <code>topic</code>, <code>op</code>, <code>ts</code>). Your code can reuse a Pinnacle parser unchanged.</p>
    <p style="font-size: 13px; color: var(--muted); margin: 8px 0 0"><b>Frame flow on firehose subs.</b> <code>live</code>, <code>prematch_matchups</code> and <code>prematch_markets</code> frames all flow on <code>sport_ids</code> subscriptions exactly the same way they do on <code>event_ids</code> subscriptions. There's no event-id-only mode &mdash; the filter is identical, only the criterion (whole sport vs. specific ids) changes.</p>

    <h4>Frame semantics — how to read what we forward</h4>
    <p>Pinnacle pushes incremental updates over MQTT. Once you start receiving frames, the <code>op</code>, <code>topic</code>, and inner <code>rec</code>/<code>data</code> shape determines how to merge into your local state.</p>

    <h5 style="margin: 14px 0 6px; color: var(--text); font-size: 13px; text-transform: uppercase; letter-spacing: .1em">Live frames — <code>type:"live"</code></h5>
    <table style="width: 100%; margin: 0 0 14px">
      <thead><tr><th>Field</th><th>Type</th><th>Meaning</th></tr></thead>
      <tbody>
        <tr><td class="name">op</td><td class="type">string</td><td class="desc" id="ws-del"><b>add</b> = new event or new markets appeared. <b>upd</b> = incremental change (typically just changed markets &mdash; merge by composite key, don't replace the whole list). <b>del</b> = this event has no open markets right now &mdash; drop your local copy of its prices. <b>It does not mean the match is over.</b> A temporary suspension (between points, an injury stoppage, a VAR check) produces a <code>del</code> too, and the event returns with a fresh <code>upd</code> when the markets reopen. Your subscription stays active across a <code>del</code>, so you keep receiving those updates without re-subscribing &mdash; treat <code>del</code> as state invalidation, not completion.</td></tr>
        <tr><td class="name">topic</td><td class="type">string</td><td class="desc">Source MQTT topic. Format: <code>matchups/reg/sp/{arcadia_sid}/live/{ld|dz|both}</code> for live, <code>matchups/.../pre</code> for prematch.<br><b>ld</b> = "line drawing": main markets (moneyline, 1X2, primary spread/total).<br><b>dz</b> = "draft zone": alternative spreads and totals.<br><b>both</b> = combined push covering both.<br><code>matchups/spc/...</code> instead of <code>reg</code> means a "special" matchup (props, futures).</td></tr>
        <tr><td class="name">rec.id</td><td class="type">int</td><td class="desc">Pinnacle matchup ID. Stable across the event's lifetime.</td></tr>
        <tr><td class="name">rec.markets</td><td class="type">array</td><td class="desc">May be a SUBSET on <code>op:"upd"</code> — Pinnacle only sends what changed. <b>Merge by composite key</b> (<code>m.key</code> if present, otherwise <code>type|period|side|points</code>). A market with <code>m.status !== "open"</code> is a CLOSE signal: drop it from your local list, do not merge it back as if still active.</td></tr>
        <tr><td class="name">rec.periods</td><td class="type">array</td><td class="desc">Per-period status. <code>periods[n].status === "closed"</code> or <code>"settled"</code> implicitly closes ALL markets for that period — drop those locally too, even if they weren't listed in <code>markets</code>.</td></tr>
        <tr><td class="name">rec.parentId</td><td class="type">int?</td><td class="desc">If present, this is a CHILD matchup (alt periods, props derived from a parent event). Its full metadata (participants, league) lives on the parent record.</td></tr>
        <tr><td class="name">rec.startTime, status</td><td class="type">string</td><td class="desc">Event-level metadata. Tennis / Golf / Fights frequently see <code>startTime</code> updates without any market change (reschedules) — track these to surface to your users.</td></tr>
      </tbody>
    </table>

    <h5 style="margin: 14px 0 6px; color: var(--text); font-size: 13px; text-transform: uppercase; letter-spacing: .1em">Prematch frames — <code>prematch_matchups</code> + <code>prematch_markets</code></h5>
    <table style="width: 100%; margin: 0 0 14px">
      <thead><tr><th>Field</th><th>Type</th><th>Meaning</th></tr></thead>
      <tbody>
        <tr><td class="name">type</td><td class="type">string</td><td class="desc"><code>prematch_matchups</code> = response from <code>/sports/{sid}/matchups</code>. The full per-sport matchup list, fired every 5 s. <b>Includes both prematch and live entries</b> — filter by <code>data[i].isLive === false</code> if you want strict prematch.<br><code>prematch_markets</code> = response from <code>/matchups/{id}/markets/related/straight</code>. Fired only when Pinnacle bumped <code>matchup.version</code>, so roughly the events that had market activity in the last cycle.</td></tr>
        <tr><td class="name">data</td><td class="type">array</td><td class="desc">For <code>prematch_matchups</code>: array of full matchup records (event metadata). For <code>prematch_markets</code>: array of market objects scoped to one matchup.<br><b>This is the authoritative current snapshot from Pinnacle</b> — any market in your local store that's NOT in this list has been closed by Pinnacle. Drop it.</td></tr>
        <tr><td class="name">matchup_id</td><td class="type">int</td><td class="desc">(prematch_markets only) The matchup this markets array belongs to.</td></tr>
        <tr><td class="name">mode</td><td class="type">string?</td><td class="desc">Present only when MQTT is down and we fell back to live REST polling. Value: <code>"rest_fallback"</code>. Frame shape is otherwise identical, so customers usually ignore this field.</td></tr>

    <h5 style="margin: 14px 0 6px; color: var(--text); font-size: 13px; text-transform: uppercase; letter-spacing: .1em">Merge recipe (pseudocode)</h5>
<pre><span class="c">// Maintain a Map&lt;matchupId, MatchupState&gt;. For each incoming frame:</span>

<span class="k">if</span> (msg.type === <span class="s">"snapshot"</span>) {
  <span class="k">for</span> (<span class="k">const</span> ev <span class="k">of</span> msg.events) state.set(ev.id, ev);
}

<span class="k">if</span> (msg.type === <span class="s">"live"</span>) {
  <span class="k">if</span> (msg.op === <span class="s">"del"</span>)  { state.delete(msg.rec.id); <span class="k">return</span>; }
  <span class="k">const</span> existing = state.get(msg.rec.id) ?? {};
  <span class="k">const</span> merged = { ...existing, ...msg.rec };
  <span class="k">if</span> (msg.rec.markets) {
    <span class="k">const</span> byKey = <span class="k">new</span> Map((existing.markets ?? []).map(m =&gt; [marketKey(m), m]));
    <span class="k">for</span> (<span class="k">const</span> m <span class="k">of</span> msg.rec.markets) {
      <span class="k">if</span> (m.status &amp;&amp; m.status !== <span class="s">"open"</span>) byKey.delete(marketKey(m));   <span class="c">// close signal</span>
      <span class="k">else</span> byKey.set(marketKey(m), m);
    }
    merged.markets = [...byKey.values()];
  }
  <span class="c">// Honour period-level closes — wipe all markets for closed periods.</span>
  <span class="k">if</span> (msg.rec.periods) {
    <span class="k">const</span> closed = <span class="k">new</span> Set(msg.rec.periods.filter(p =&gt; p.status !== <span class="s">"open"</span>).map(p =&gt; p.period));
    <span class="k">if</span> (closed.size) merged.markets = merged.markets.filter(m =&gt; !closed.has(m.period ?? <span class="n">0</span>));
  }
  state.set(msg.rec.id, merged);
}

<span class="k">if</span> (msg.type === <span class="s">"prematch_markets"</span>) {
  <span class="c">// AUTHORITATIVE snapshot for one matchup — replace, don't merge.</span>
  <span class="k">const</span> existing = state.get(msg.matchup_id) ?? {};
  state.set(msg.matchup_id, { ...existing, markets: msg.data });
}

<span class="k">function</span> marketKey(m) {
  <span class="k">return</span> m.key ?? <span class="s">`${m.type}|${m.period ?? 0}|${m.side ?? ""}|${m.prices?.[0]?.points ?? ""}`</span>;
}</pre>

    <p style="font-size: 13px; color: var(--muted); margin: 8px 0 0"><b>Reconnect strategy.</b> Re-subscribe on reconnect. Server-side state is not preserved — the snapshot at the start of every connection is your sync point. Exponential backoff (1s → 2s → 4s → 30s cap) recommended. One connection per account on this endpoint (separate slot from SSE — you can run both).</p>

<h2 id="tennis">Tennis: sets and games</h2>
<p>A tennis match is <b>two events</b>, not one. Sets live on the match; games live on a separate <code>(Games)</code> event that points back through <code>parent_id</code>. Read only the first row and you will see a handicap of &plusmn;1.5 and mistake the <em>set</em> handicap for the game handicap.</p>
<table class="param-table">
  <thead><tr><th>Event</th><th>What its <code>periods</code> hold</th></tr></thead>
  <tbody>
    <tr><td class="name">The match<br><span class="type">parent_id: null</span></td><td class="desc"><code>money_line</code> match winner &middot; <code>spreads</code> <b>set</b> handicap (&plusmn;1.5, &plusmn;2.5) &middot; <code>totals</code> total <b>sets</b>. <code>num_0</code> is the whole match, <code>num_1</code> is set 1.</td></tr>
    <tr><td class="name">&hellip; (Games)<br><span class="type">parent_id: match id</span></td><td class="desc"><code>spreads</code> <b>game</b> handicap (&plusmn;4.5, &plusmn;5.5) &middot; <code>totals</code> total <b>games</b> &middot; <code>team_totals</code> per-player game totals.</td></tr>
  </tbody>
</table>
<p>Both rows come back <b>by default</b> — no parameter needed — on <a href="#markets"><code>/kit/v1/markets</code></a>, <a href="#details"><code>/kit/v1/details</code></a> and <a href="#prematch-markets"><code>/kit/v1/prematch/markets</code></a>. On <a href="#prematch-lines"><code>/kit/v1/prematch/lines</code></a> the child arrives in a <code>children</code> array next to the match's own <code>periods</code>.</p>
<pre><span class="c">GET /kit/v1/prematch/markets?event_id=1635918998</span>

{
  <span class="k">"events"</span>: [
    {
      <span class="k">"event_id"</span>: <span class="n">1635918998</span>,
      <span class="k">"parent_id"</span>: <span class="k">null</span>,
      <span class="k">"periods"</span>: { <span class="k">"num_0"</span>: { <span class="k">"spreads"</span>: { <span class="s">"1.5"</span>: {...}, <span class="s">"-1.5"</span>: {...} } } }   <span class="c">// set handicap</span>
    },
    {
      <span class="k">"event_id"</span>: <span class="n">1635954125</span>,
      <span class="k">"parent_id"</span>: <span class="n">1635918998</span>,

<p><b>Build against this rule:</b> treat a match as a family, not a row — collect every event where <code>event_id == X</code> <b>or</b> <code>parent_id == X</code>. Not every match has a <code>(Games)</code> child: doubles and smaller tours often have none, because Pinnacle posts no game line for them. An empty result there is real coverage, not a gap.</p>
<p><b>Tournament futures are separate again.</b> Outrights such as <span class="s">"ATP US Open 2026 Winner"</span> belong to a tournament rather than a match, so they carry <code>parent_id: null</code>, an empty <code>periods</code>, and their prices under <code>special_markets</code>. They appear only on the sport-wide call with <code>include_specials=1</code>, never on a single-match call.</p>

    <span class="k">"home_stats"</span>: [{ <span class="k">"period"</span>: <span class="n">0</span>, <span class="k">"score"</span>: <span class="n">1</span>, <span class="k">"redCards"</span>: <span class="n">0</span> }, { <span class="k">"period"</span>: <span class="n">1</span> }],
    <span class="k">"away_stats"</span>: [{ <span class="k">"period"</span>: <span class="n">0</span>, <span class="k">"score"</span>: <span class="n">0</span>, <span class="k">"redCards"</span>: <span class="n">0</span> }, { <span class="k">"period"</span>: <span class="n">1</span> }]
  }
}</pre>

<p>Two things about this object are worth spelling out, because guessing wrong fails silently rather than loudly.</p>

<div class="callout">
  <b>The two <code>last</code> fields are unrelated.</b> One sits at the top of the response beside <code>sport_id</code>, the other inside every event. They share a name and nothing else.
  <ul>
    <li><b>Top level — <code>last</code> and <code>last_call</code>.</b> A sequence counter for our store, not a time. It only moves forward, it is shared across the whole store rather than being per-sport, and it is the value you pass back as <code>since=</code>. It reads like <code>338194</code>, so comparing it against a clock will not do anything sensible.</li>
    <li><b>Inside each event — <code>last</code>.</b> Unix seconds, UTC — but recorded when we serialised <em>your response</em>. <b>Every event in one response carries the identical value</b>, equal to the HTTP <code>Date</code> header. One call to <code>/kit/v1/prematch/fixtures?sport_id=5</code> returned 116 events sharing a single <code>last</code>. It records when you asked, not when the odds moved.</li>
  </ul>
  <p style="margin-bottom:0">So the per-event <code>last</code> is <b>not</b> a "last updated" marker and cannot tell you whether a price is fresh. There is no per-price observation timestamp in these payloads. To find out what actually changed, send the top-level <code>last</code> back as <code>since=</code> and see which events return.</p>
</div>

<p><b><code>parent_id</code> means this event belongs to another one.</b> It is <code>null</code> for a normal match. Where it is set, the row is part of a family — the clearest case is tennis, where games markets live on a separate <code>(Games)</code> event pointing back at the match; see <a href="#tennis">Tennis: sets and games</a>. Special-market rows use the same link. Collect <code>event_id == X || parent_id == X</code> to get a whole match rather than one row of it.</p>

<h2 id="live-state">Live state object</h2>
<p>Live events carry a <code>state</code> object holding in-game data, forwarded from Pinnacle exactly as it lands on their MQTT feed. The field names are sport-specific and we leave them untouched. An event with no in-game state at all returns <code>state</code>: <code>null</code> rather than an empty shell, so <code>if (event.state)</code> is enough to branch on.</p>

<p>The object breaks down into three top-level fields:</p>
<ul>
  <li><code>state.match</code> — overall match-level state (clock / current period). Sport-dependent.</li>
  <li><code>state.home</code> / <code>state.away</code> — current state for each participant.</li>
  <li><code>state.home_stats</code> / <code>state.away_stats</code> — array indexed by period, only populated when Pinnacle has published a stat value for that period.</li>
</ul>

<p style="color: var(--muted); font-size: 13px; margin-top: 8px"><b>Heads-up:</b> a field only shows up once Pinnacle has a real value for it — <code>corners</code>, for instance, stays absent in soccer until the first corner is taken. Assume every field is optional and code defensively.</p>

<p style="color: var(--muted); font-size: 13px; margin-top: 8px"><b>Coverage varies by sport.</b> Tennis, basketball and hockey carry <code>state.match</code> on effectively every in-play event. Soccer runs lower — a clock is not published for every competition — and esports currently carries none. A <code>null</code> <code>state.match</code> on a live event means "not published upstream for this match", not an error, and it can fill in partway through a game.</p>

<p><b>Where you'll find it:</b> <code>GET /kit/v1/markets?event_type=live</code> is the endpoint to reach for. The prematch endpoints (<code>/kit/v1/prematch/*</code>) return <code>state</code>: <code>null</code> for genuine pre-game fixtures, but a match that has already kicked off can linger in the prematch store briefly and carry partial state there — participant <code>score</code>, <code>corners</code>, <code>yellowCards</code> — with <code>state.match</code> still <code>null</code>. Don't build on prematch for game state, but do handle it being present. The <code>/odds-drop</code> SSE stream omits the <code>state</code> object entirely.</p>

<p><b>Top-level clock fields.</b> Alongside <code>state</code>, every event object also carries <code>quarter</code> and <code>time_remaining_in_qtr</code>, lifted out of the match state for sports where a quarter clock is published (basketball today). They are <code>null</code> everywhere else. These two are the one piece of game state that also rides the <code>/odds-drop</code> SSE stream — appended to a drop payload only when non-null, so consumers on other sports see an unchanged wire shape.</p>
